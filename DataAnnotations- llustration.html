How Teaching Fits Data Annotation

During my Ph.D. and years teaching Computer Science, I spent hundreds of hours reading student code and writing grading rubrics. You quickly learn that vague instructions lead to subtle bugs, especially around missing values, data types, and edge cases.

Evaluating AI-generated code in RLHF works the same way. Models often write code that looks right at a glance but breaks on messy data. Good annotation means catching those quiet failures and explaining clearly why one implementation is safer than another.

Example 1: Python & Pandas Evaluation

Prompt: "Write a Python function using pandas to calculate average revenue per region, ignoring invalid negative entries."
Response A — Edge-Case Bug
def avg_rev(df):
    df = df[df['rev'] > 0]
    return df.groupby('region')['rev'].mean()
Response B — Preferred
def avg_rev(df: pd.DataFrame) -> pd.Series:
    valid = df.loc[df['rev'].ge(0)].dropna(subset=['region'])
    return valid.groupby('region')['rev'].mean()
Preference: Response B
  • Zero values: The prompt only asks to ignore negative numbers. Response A uses > 0, which accidentally drops valid $0 revenue rows. Response B uses .ge(0) to keep them.
  • Missing regions: Response B explicitly drops rows where region is null so grouping behaves predictably.
  • Clarity: Type hints in Response B make the expected input and output clear without adding unnecessary complexity.

Example 2: SQL Query Evaluation

Prompt: "Write a SQL query to get the total number of orders for every user, including users who have placed zero orders."
Response A — Drops Zero-Order Users
SELECT u.user_id, COUNT(o.order_id) AS total_orders
FROM users u
JOIN orders o ON u.user_id = o.user_id
WHERE o.status = 'completed'
GROUP BY u.user_id;
Response B — Preferred
SELECT u.user_id, COUNT(o.order_id) AS total_orders
FROM users u
LEFT JOIN orders o 
  ON u.user_id = o.user_id 
  AND o.status = 'completed'
GROUP BY u.user_id;
Preference: Response B
  • Join logic: Response A uses an inner JOIN, which completely removes users with zero orders from the output. Response B uses a LEFT JOIN to preserve all users.
  • Filtering placement: Filtering o.status inside the WHERE clause (as in Response A) turns a left join back into an inner join. Putting that condition in the ON clause keeps zero-order users with a count of 0.
  • Count accuracy: Both correctly use COUNT(o.order_id) instead of COUNT(*), ensuring null rows aren't counted as orders.
